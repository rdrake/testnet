After `RENAME #old #new`, chathistory acted as if `#new` had just been created. `m_rename.c` (classic RENAME and the relocate form) had no chathistory hook: the rows stayed under `#old`, `#new` started with no history, and `#old`'s rows could no longer be reached once the old name was gone.

This follows the direction in ircv3/ircv3-specifications#532: the channel has always been this name. Its history before the rename is returned under the current name, in one time order with what came after.

**The fix: a mapping, with no rows rewritten.**
- A new RocksDB column family, `renames`, holds one record per current channel name, keyed by the folded name like the other name keys.
- Each entry names an earlier name, the channel's incarnation (its creationtime, which a rename keeps), and the millisecond the channel left that name.
- The rows that count as the channel's history are those under the earlier name that carry that incarnation and are stamped before the rename. So a channel later created under `#old` (another creationtime) does not mix with the renamed one in either direction. A relocation tombstone (same creationtime) keeps what it stores after the move.
- Records are flat, so nothing is followed at read time. Renaming `#b` to `#c` moves `#b`'s entries into `#c`'s record and adds `#b`. A loop such as `#a→#b→#a` drops the entry for the record's own name. Each incarnation keeps its 16 latest names.
- Entries behind the retention floor are dropped. Rows under old names age out exactly as before, and the trim engine is unchanged.
- Every server records the rename itself when it applies it: in `rename_channel()` (local or S2S), `relocate_execute()`, and `relocate_again()` for the winner of a crossing. Federation needs no wire change, because `CH Q` names the current name and each store answers from its own record.

**Read side.** A merged cursor walks the target's own rows together with every earlier-name segment, in key order, and presents each row under the current name. It covers:
- LATEST, BEFORE, AFTER, AROUND, BETWEEN and SEARCH;
- msgid resolution (AROUND/BETWEEN by msgid, REDACT, `CH Q X`);
- reply and redaction lookups;
- TARGETS, including a renamed channel nobody has spoken in since;
- the receive-coverage check;
- the burst-loss prune, which also drops the losing incarnation's rows under earlier names.

**Not done:**
- No RENAME event row is stored or replayed. A RENAME line inside a batch already shown under the new name would tell a `draft/channel-rename` client to rename a buffer it does not have. The record keeps the old name and time if one is wanted later.
- A server that never applied the rename (down or split at the time) has no record, so its `#old` rows do not show under `#new`. Fixing that needs the burst to carry former names.
- With `CHATHISTORY_STRICT_PRESENCE` on (off by default), presence intervals are keyed by name and do not follow a rename. Read markers and channel metadata are also still keyed by the old name.
- Rows from before incarnation stamps (2026-09-08) are not carried, since only rows provably of the renamed channel move.

**Testing:**
- New CMocka suite `history_rename_cmocka`, 18 cases. It runs on an in-memory store and, as `history_rename_rocksdb_cmocka`, on real RocksDB, including a close and reopen.
  - The cases cover chains, a there-and-back loop, the cap, incarnations apart, the floor and sweep, limits and cursors across the boundary, a recreated old name, a case-only rename, and an unreadable record.
  - All 18 fail against a stub and pass after.
- `rename_handlers_cmocka` checks that a relocation records the rename and that both orders of a crossing leave the winner with it. All suites pass.
- `history.c`'s read paths are not linked by any suite, so they were checked live on one server:
  - Three messages in `#old`, then `RENAME #old #new`, then two more: `CHATHISTORY LATEST #new * 50` returns all five as `#new`, in order. The base build returns two.
  - BEFORE, AFTER, AROUND and BETWEEN page across the rename with msgids from either side. TARGETS lists `#new`.
  - The chain `#old→#new→#newer→#new` returns each row once.
  - Another user recreating `#old` sees only their own row.
  - REDACT from `#new` of a message stored under `#old` works, and so do reactions to it.
  - A base build starts on a store that has the new column family.
- Federation was not checked live.
