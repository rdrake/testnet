A bouncer device's NICK is a request to its primary's server (BX W). The device's server remembers the pending request in `cli_nickask_ts`, so a late answer can be told apart from a fresh one. Any 432, 433, 437 or 438 delivered to the device cleared that memory. So a refusal of an earlier request cancelled the next one: with `NICK x1` then `NICK x2` inside one round trip, x1's refusal cleared x2's request, x2's answer was dropped as stale, and the device heard nothing about it.

**The fix:** a refusal numeric clears the pending request only when the nick it refuses is the nick asked for last. That nick is the first word of `parv[2]`, which holds the rest of the numeric's line. 437 names a channel, not the nick, so it no longer clears anything; its request lapses at `NICK_ASK_RETURN_WINDOW` like any other unanswered one.

**Testing:** new CMocka suite `nickask_cmocka` runs `do_numeric()` on:
- 433, 432 and 438 for the asked nick: the request is cleared;
- an earlier, a longer and a shorter nick: the request is kept;
- 437: the request is kept.

Its first case also caught a bug in this PR's first commit, which compared against the whole rest of the line and so never matched; the second commit fixes it. All suites pass.
