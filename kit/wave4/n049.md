Two ordering bugs in the event loop:
- `socket_del()` and `socket_del_keepfd()` dropped a pending engine error and then called the engine's `eng_closing` hook, which can raise one itself (devpoll's POLLREMOVE write). That error stayed counted after the socket left the list, and `socket_run_errors()` later found a count with no socket to deliver it to.
- `server_die()` closes every descriptor and clears `running`, but every engine went on with the rest of its event batch, then the timers and the thread pool. Handlers ran on closed descriptor numbers. Traces showed the IAuth socket's EOF respawning IAuth during shutdown, and a teardown can write to a number that a new open just took.

**The fix:**
- `eng_closing` runs first, then the drop, as on master.
- All five engines stop dispatching the rest of their batch once `running` is 0, and skip that pass's timers.

**Testing:**
- `ircd_events_cmocka` adds a case for an error raised while deleting; it failed before the change.
- `auth_recheck_cmocka` used to end its loop by clearing `running` from a socket callback and expected that pass's timers to run anyway. It now ends the loop from a timer.
- All suites pass.
- No test asserts the new `running` break directly.

**Still run after DIE, as before:**
- the second event of the socket being handled (ET_WRITE after ET_READ);
- further signals read in the same `signal_callback()` pass;
- the rest of the DIE caller's own stack.

Master already had the delete ordering. Its separate DESTROY-ordering fix is opened against master on its own.
