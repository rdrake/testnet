The `PERSISTENCE` command and the `draft/persistence` capability carried two things:
- the specification's surface: STATUS, GET and SET;
- the fork's own extras: ATTACH, DETACH, LIST, PROFILE and REPLAY.

Two names on the wire were also defined nowhere:
- A held session's restored channel state came in a batch typed `draft/persistence`. The persistence draft defines no batch type.
- The server advertised a `draft/bouncer` capability that nothing read.

This PR follows the agreed direction:
- **New capability `evilnet.github.io/persistence`.** It carries the extras, and its value now holds the tokens (`attach,detach,list,attach-cursor`). `draft/persistence` has no value, because the spec defines none. STATUS, GET and SET stay on `draft/persistence` and already follow the spec: a refused SET sends a WARN and the unchanged STATUS.
- **The extras need the vendor capability.** `PERSISTENCE_DRAFT_EXTRAS` (default TRUE) is a transition: it lets a client that negotiated only `draft/persistence` keep using them. Set it to FALSE once clients have moved; without either capability, the extras are unknown subcommands. The gate checks the connection's own caps, not the bouncer session's union.
- **The restore batch is typed `evilnet.github.io/persistence`.**
- **`draft/bouncer` is gone.** `CAP_draft_bouncer` remains as an obsolete setting that nothing reads, so existing configurations still load.

**Clients:** Seance already requests both capabilities, reads `attach-cursor` from either one's value, and accepts either batch type. The testnet test that expects `draft/bouncer` to be advertised needs updating.

**Testing:** build and all CMocka suites pass. I also checked on a running server:
- CAP LS shows `evilnet.github.io/persistence=attach,detach,list,attach-cursor` and a bare `draft/persistence`.
- `PERSISTENCE LIST` with neither capability gets `FAIL ... INVALID_PARAMETERS ... Unknown PERSISTENCE subcommand`.
- With either capability it reaches the subcommand.
