Three places sent a client more than it had negotiated.

- **CAP NEW and DEL carried CAP 302 additions to every cap-notify client.** CAP LS gives capability values (`sasl=PLAIN,EXTERNAL`, `draft/multiline=max-bytes=...`) and `sts` only to a `CAP LS 302` client. `cap_notify_flush()` and `send_cap_notify()` sent them to everyone. A client that asked with a plain `CAP LS` now gets bare names and no `sts`.
  - `cap_batch_line()` also stops at the end of its buffer. The old code wrapped `buflen - len` as a `size_t`.
- **Client-only tags from a client without message-tags.** `parse_client()` accepts an `@`-tagged line from a client that negotiated only batch, labeled-response or server-time, so that labels and `@time` work. It also kept and relayed that line's `+` tags.
  - `+` tags are now taken only from a connection that negotiated message-tags itself.
  - TAGMSG does nothing for a client without message-tags, so it is no longer relayed or echoed.
- **Bouncer devices were treated as having their session's caps.**
  - `send_multiline_fallback()` added client-only tags to a device based on the caps of its whole session. It now checks the device's own, as the batch opener already does.
  - CAP NEW and DEL went to a device that never asked for cap-notify, because its primary had (`cap_notify_wanted()` read the session's union of caps). It now checks the connection's own caps.

**Not fixed here:** `CAP_BATCH_BUFSIZE` is 1024, but `sendrawto_one` cuts a line at 510 bytes. A large change in one REHASH can still cut a capability name in the middle.

**Testing:** build and all CMocka suites pass. I also checked on a running server, after a REHASH that changes `MULTILINE_MAX_LINES` and turns on `CAP_sts`:
- A cap-notify client registered with a plain CAP LS gets `CAP NEW :draft/multiline`. Before, it also got the value and `sts`.
- A CAP LS 302 client gets the values and `sts`, as before.
- A server-time client sending `@+x=1 PRIVMSG` no longer passes `+x` on. Its `@+x=1 TAGMSG` is neither relayed nor echoed.
