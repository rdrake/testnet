# #256 description update (after the two reviews: channel in the derived msgid, HLC bound, CLEARMODE, handler tests)

## Replace the whole description with

```
Every server reveals a hidden (+D) member itself, on the event that causes the reveal: a message, a TOPIC, a MODE that gives the member a status, or `-D`. That JOIN is not relayed. Each server minted its own msgid for it and stored its own row. Members on different servers therefore saw the reveal under different msgids, and federated history merged it once per server.

**The fix: the JOIN's msgid is derived, not minted and not carried.**
- Every server already has the msgid of the event that causes the reveal. It also has the channel's name and the member's numeric.
- `msgid_derive_join()` makes the JOIN's msgid from those three. Every server that handles the event under one msgid gets the same JOIN msgid. Nothing is added to the wire.
- The id has the minted layout and decodes like a minted id. Its time is the event's time less 1 ms, so the JOIN sorts before the event it precedes on every server, in live `@time` and in history.
- Bit 15 of its logical field is set. The other 39 bits beside the time (node, the rest of logical, counter) are a hash of the event's msgid, the channel's name in lower case and the member's numeric.
- A msgid minted by a server with this change has bit 15 clear. The HLC's logical counter now carries into the time at 0x7FFF, for its own count and for a larger one a peer hands in. Before, it carried at 0xFFFF, so 32768 events at one clock reading set the bit.
- Two reveals a millisecond or more apart never share an id. Two reveals in the same millisecond that differ in event, channel or member share an id with probability 2^-39 (1 in 5.5e11). The layout has no room for more.

**Where the event's msgid comes from:**
- A line from another server: the msgid the line arrived with.
- An event that starts here, or a line that arrived without tags: the event's code mints its msgid after the reveal. The reveal takes that id ahead of time with `generate_msgid_ahead()`, and the next `generate_msgid()` returns it. An id that no event takes is dropped at the end of the line. It is also dropped if the clock has moved on, because an event reads its time from the clock right after its mint.
- A multiline batch mints its msgid before it reveals, so it passes that msgid in.

**What this replaced.** An earlier version of this branch carried the JOIN's msgid on the event's line in a new tag segment, `,J<numeric><msgid>`. That is gone, with everything that carried it: the field in `struct Connection`, the parse, the armed override, the save and restore across the two MODE sends and across a multiline batch's links, the per-target reset in TOPIC, and the change to `sendcmdto_one()`. `send.c`'s senders, `parse.c` and `client.h` are as they were before this branch.

**What the derived id covers that the segment did not:**
- A line that reveals several members (a MODE on two hidden members, or `-D` showing everyone) gives each of them a shared msgid. The segment carried one.
- A line that names two channels gives the member one JOIN msgid per channel.
- A server without multiline behind a relaying hub derives from the batch msgid on its first fallback line. The segment did not reach it.
- An older server in the path no longer cuts the sharing for an event it relays with its msgid (a message, a TOPIC, a MODE, a multiline batch). It mints its own JOIN msgid, as before, and the servers on either side of it agree with each other.
- The JOIN sorts before its event whatever the mint order was. Before, a message or a batch from an untagged origin minted its own msgid before the reveal, and the JOIN sorted after it.

**MODE:** a MODE too long for one line is flushed as two, each with its own msgid. The flush now takes the room of its status changes first, so a `+o`, `+h` or `+v` always goes out in the first MODE. That is the MODE the reveal took its id from, and the one the other servers get the status under. A ban or a key that no longer fits goes in the second MODE, as before. The order of the letters and parameters is unchanged.

**TOPIC:** `do_settopic()` reveals a hidden setter before it mints the TOPIC's msgid and reads its time. Before, on an untagged TOPIC, the live `@time`, the row and the relayed time drifted from the msgid's mint by the reveal's work.

**CLEARMODE:** every server makes the MODE of a CLEARMODE itself. With `JOIN_ON_REMOVEDELAY` on, a `-D` in it shows the hidden members. The CLEARMODE was relayed without tags, so each server minted its own MODE msgid and derived its own JOIN msgids. It now carries the MODE's msgid and time: the ones it arrived with, or those of the first MODE made here.

**A line whose time was replaced:** `parse.c` replaces the time of a line whose sender's clock is more than `HLC_MAX_FORWARD_MS` ahead, and keeps its msgid. The JOIN keeps its derived msgid. Its time is the line's time less 1 ms when the derived id's own time would not be before the line's.

**Limits:**
- A server that gets the event without a msgid (a legacy link, or `P10_MESSAGE_TAGS` off) mints one for the event, and derives from that. It agrees with the servers behind it, not with the origin. The event itself has the same split today.
- An older server relays a CLEARMODE without tags. The servers behind it derive from their own MODE msgids, as before.
- An event msgid that is not in the minted form (another implementation's) gives a JOIN msgid minted per server, as before.
- A server on an older build can still mint a msgid with bit 15 set, after 32768 events at one clock reading. A server with this change that receives that count carries past it.
- A TOPIC that is refused for colour after the reveal shows the JOIN on the setter's server only, as before. No other server has its msgid.
- With a replaced line time, the JOIN's `@time` and row are before the event, but the time inside its msgid is still the sender's.

**Not covered here:** netjoin JOINs after a burst and the QUITs of remote users on a netsplit, KILL or collision also get a per-server msgid. They are a separate change.

**Build:** the compile rules in `ircd/Makefile.in` and `ircd/test/Makefile.in` now pass `-MMD -MP` and read the `.d` files back. Before, the test objects had no header dependencies and the `make depend` list knew 195 of 270 objects, so a change to a header could leave an object with the old layout until `make clean`. In `ircd/test` the `make depend` rule compiles without `-MMD -MP`.

**Docs:** the p10-protocol skill's msgid section has the current minted layout and the derived form.

**Changed after review:**
- MODE split: `MODE #c +bbbv <three long masks> nick` gave the origin a JOIN msgid from the first MODE and every other server one from the second. Status changes now always go in the first MODE.
- Future time: with a sender's clock past `HLC_MAX_FORWARD_MS`, the JOIN was stamped in the future, after its event. It now takes the line's time less 1 ms.
- TOPIC on two channels: `TOPIC #a,#b` with `#a` refusing the topic after its reveal gave the user's JOINs in `#a` and `#b` one msgid. The channel's name is now part of the derivation.
- Fold: the id carried 9 bits of the event's msgid, so two events in one millisecond gave one member the same JOIN msgid 1 time in 512, and always when the ids were 18 mints apart. The id is now a 39-bit hash of event, channel and member.
- Bit 15: nothing kept it out of minted ids. The HLC's logical counter now stops at 0x7FFF.
- CLEARMODE: it is relayed with its MODE's msgid.
- clang: `make depend` in `ircd/test` ran with `-MMD -MP` and `-MM` together. clang then appended preprocessed source to `Makefile.in`, and gcc appended nothing. The rule now runs without `-MMD -MP`. Checked with clang 18 and gcc.
- Tests: the reveal cases ran against a copy of the minting code and stubbed sends. `reveal_handlers_cmocka` drives the real handlers.

**Testing:** build with no new warnings. All 94 CMocka suites pass. New cases:
- `ircd_string_cmocka`, `test_msgid_derive_join`: the id decodes, is 1 ms before the event and has bit 15 set. The same inputs give the same id, also with the channel's name in another case. Another member, another channel or another event gives another id. 4096 events of one millisecond give 4096 ids. A malformed event id, a missing argument or a short buffer gives none.
- `crdt_hlc_cmocka`, `test_logical_stops_below_bit_15`: 40000 events on a pinned clock never give a logical above 0x7FFF and stay in order. A peer's larger logical carries.
- `send_s2s_tags_cmocka`, `test_msgid_ahead_is_the_next_mint`: an id taken ahead is returned by the next `generate_msgid()`, once. It is also the id a tag region mints when no handler minted. The end of the line drops it. A clock that has moved on drops it.
- `channel_speak_cmocka`, five cases on the real `RevealDelayedJoin()` and modebuf flush: a line from another server gives the derived id and time with nothing minted, for two members of one line. An event that starts here, or an untagged line, gives the id derived from the msgid the event's own mint then gets. A given event msgid is used as is, and one that is not a minted one falls back to a local mint. A line whose time was replaced gives a JOIN before it. A MODE split over two lines names the JOIN after the MODE with the status change.
- `reveal_handlers_cmocka` (new suite), four cases. It runs `m_topic()`, `ms_topic()`, `m_mode()` and `mo_clearmode()` with the real `channel.c`, `send.c` and HLC. It formats every line and reads the msgid and time off the lines a watching client and the next server get. `TOPIC #a,#b` with `#a` refused: two JOINs, two msgids, and `#b`'s is the one derived from the TOPIC's. `MODE +bbbbbv` too long for one line: the JOIN is named after the MODE with the `+v`, which is the msgid on the line to the next server. A TOPIC on two channels from another server with a msgid 5 minutes ahead and a replaced time: each JOIN has the derived id and is 1 ms before its TOPIC. `CLEARMODE #d D`: the line to the next server has the msgid the two JOINs derive from. Each case fails without its fix. The replaced time is set on the link as `parse.c` leaves it; `parse.c` itself is not run.

Live, on three linked servers A, B and C in a line, with watchers on all three and hidden members on B and C. I compared the JOIN's msgid and `@time` on each server, live and in `CHATHISTORY LATEST`:
- PRIVMSG, NOTICE, TOPIC, WALLCHOPS, a multiline batch: one msgid on all three, 1 ms before the event.
- `MODE +vv` on two hidden members, and `-D` with two hidden members: each member's JOIN has one msgid on all three.
- `MODE +bbbbbv` with five masks and a hidden nick, sent on A: two MODEs, and the JOIN has one msgid on all three, 1 ms before the MODE with the `+v`.
- `TOPIC #a,#b :<colour>` by a user on B hidden in both, `#a` set `+c`: B shows two JOINs with two msgids. `#b`'s is the same on all three.
- `CLEARMODE #c D` by an oper on A with `JOIN_ON_REMOVEDELAY` on: each of the two members' JOINs has one msgid on all three.
- A and C on this branch with B on the base build: A and C agree on a message, a TOPIC, `MODE +vv`, the split MODE, `-D` and a multiline batch. B mints its own, as before. After a CLEARMODE, A, B and C each have their own. The link and the reveals work.
```
