Reviewed at ce86335a. Built (0 warnings) and as an ASan build, and run on two- and three-server scratch networks, also with the base build on either side of the link: no ASan reports, no crash. CMocka was not run at this head (the file has no suite).

The case the PR is for works (run): a bouncer device on A whose primary is on B finds rows only B holds with a plain `SEARCH text=...`; on the base it found none. Rows held by two stores appear once, `limit` applies across channels, the label is on the batch, and SQUIT, a client quit and late replies mid-search were clean under ASan.

1. **A query whose `CH Q S` line cannot fit is answered from this server only, with no error.** `start_fed_search()` returns NULL when the measured line reaches 510 bytes (`ircd/m_chathistory.c:8238`), and both callers then answer locally: the `in=` path (:9941-9948) and the new per-channel loop (:10000-10003). The selector-length check at :9897-9905 refuses an oversize text with `FAIL SEARCH INVALID_PARAMS` "so local and federated behaviour agree", and #242 refuses an over-long `in=` line the same way; this one is silent. Run: a 190-character channel and a 270-character `text=`: the base's `in=` sent a cut line and still found the matching row; this head returned 0 rows for both forms. Proposed: refuse with `INVALID_PARAMS` when the line cannot fit, so both forms and #242 follow one rule.
2. **Each no-`in=` SEARCH costs every storage peer about 2.1-2.2 s of main loop.** Each part gets the full `SEARCH_SCAN_MAX` of 50 000 rows on each responder (:8854), for up to `SEARCH_FED_PARTS_MAX` = 8 parts (:7870), and the walk runs in the responder's main loop, so every client there stalls. Run, with the peer holding 8 channels of 50 000 rows and a text that matches nothing: `in=#m1` kept the peer busy 0.25-0.32 s; no `in=`, 2.11-2.19 s (client latency 2.16-2.24 s). Only normal fake lag limits how often a client can send one. Which channels federate also changes what a user sees, with no signal (run): in 12 channels, only the 8 most recently joined federated; after joining more, rows found before were gone; a second SEARCH in the same write was answered locally.
3. **No tests.** Useful Vitest cases on a linked pair: a no-`in=` search finding rows only the peer holds; `limit` across channels; the label on the batch; a row held by both stores appearing once; a bouncer device whose primary is on the other server; and whatever rule is chosen for the long line and for a second search in flight. The aggregate bookkeeping (the `pending` hold, a part freed unfinished, the newest `limit` across parts) could move into `chathistory_merge.c` and be tested by CMocka without a store.
