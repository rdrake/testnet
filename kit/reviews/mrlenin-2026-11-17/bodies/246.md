**Changed after review:**
- The check's child closed every descriptor number up to the hard limit, one `close()` each: 300 ms and more at a limit of 524288. The committed `configure` does not have the `closefrom()` check yet, so Linux uses `close_range()`, and BSD the loop until it is regenerated.
- A timeout is its own result. The rehash is abandoned and not retried. `conf_file_check()` returns -2, and GitSync then puts its file back without rehashing or refusing the content.
- Errors found in a file that changed while it was checked (a write caught half done) send it back to be checked again, as a clean result already did. A valid GitSync commit is no longer refused for them.
- `ircd -k` logs nothing to the server's files or syslog. A check no longer writes "Failed to read configuration file" at CRIT into the live logs. Checked with a real binary: the old one wrote the line to the configured log file, the new one writes nothing there and still prints the error. The check runs with `argv[0]` set to the resolved binary.
- `pipe()` and `fork()` failures say why, and an exec failure names the binary.
- The check's exit is noticed with `waitid(WNOWAIT)`, and its process group is killed before it is reaped, so the group id cannot have been reused. After a timeout kill it is waited for at most a second.
- GitSync names a crash of the check as such, and no longer says "before the file was checked" after it was checked.
