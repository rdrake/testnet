Scenario: a line in `#inc`, the channel emptied and recreated, a new line. `AROUND msgid=<old line>` now gives the same page as a never-minted id at the same time (JOIN and the new line), and an empty `msgid=` gets `INVALID_PARAMS`. Fixed by the newest commit: REDACT of the dead incarnation's row now gets `FAIL REDACT UNKNOWN_MSGID`, the same reply as a never-minted id, and the `CH Q X` lookup answers `E 0` for it; a repeated REDACT of a live row still succeeds.

1. The redaction catch-up can still show members a REDACT for a message of an incarnation they never saw. By reading, not run. `redact_row_judge()` (`ircd/m_redact.c:428`, lookup at `:433`) keeps the incarnation-blind `history_lookup_message()`, so for a row this store holds only in a dead incarnation it returns APPLY, and the catch-up shows applied rows to local members. A message the store never held is a tombstone and not shown. It needs a REDACT made on one side of a split for a row whose channel the other side has since recreated, so it is rare. Fix: use `history_lookup_live_message()` there, so a dead row is judged as not held; check its write-forward caller, `process_write_forward()`, as well.

2. Nothing pins `history_lookup_live_message()`. A server test for AROUND on, and REDACT of, a dead incarnation's msgid (one server is enough) would cover both paths; CMocka cannot reach them without a store.

By reading, a tip responder can likewise still hand a PR requester the dead centre row for AROUND. Both close only once every storage server runs this; nothing changes on the wire or on disk.
