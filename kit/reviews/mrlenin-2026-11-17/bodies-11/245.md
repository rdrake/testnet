A server rolled back to an older build deleted every held bouncer session the newer build had stored.

At startup the restore pass skipped any record whose version it did not know. The eviction pass that follows then deleted every record that was neither the current version nor v7. That included the records a newer build wrote, so rolling a server back (or moving its store to an older build) lost those sessions for good.

**Newer records are kept (first commit).** A record whose version is above `BOUNCER_DB_VERSION` is recognised (`bounce_record_from_newer_build()`, and `BOUNCE_REC_NEWER` from `bounce_record_decode()`). It is logged, not restored, and not evicted, so it waits for a roll-forward. Unknown older versions, records too short for a version, and known versions of the wrong size are still evicted. A third commit makes such a rejected record run the eviction pass on its own; before, the pass ran only when something had expired, so a lone bad record stayed and was logged at every start.

**A roll-forward must not misdate the newer build's crash (second commit).** The older build keeps the newer build's records unread, but its own heartbeat keeps advancing. Rolled forward again, the newer build would read its restart markers against that heartbeat and hold the sessions from long after the crash.

- **The heartbeat carries the `BOUNCER_DB_VERSION` of the build that wrote it.** The tag goes in the pad word older builds wrote as zero, and older binaries never read that word. Zero reads as v12, the last untagged writer. A tag below 12, or past the span, means the heartbeat is corrupt.
- **A restart marker is held from the heartbeat only when the record's own build wrote that heartbeat.** Otherwise the outage is unknown, and the marker is expired with a log line of its own. This also covers a newer build that ran with its bouncer off, which rewrites only current-version markers.
- **"Newer" is bounded to `BOUNCER_DB_VERSION + 16`.** A version past that is a corrupted record, and it is evicted rather than kept forever.
- **The crash-loop breaker no longer reads a later run's heartbeat as the crashed start's.** A start that did not restore left the RUNNING boot record in place while writing heartbeats of its own. That start could have the bouncer or persistence off (a natural way out of a crash loop), or be an older build after a rollback. The next restoring start then took those heartbeats as the settle stand-in, and restored the sessions the breaker should have skipped. That gap predates this PR.
  - Such a start now runs the breaker too and consumes a RUNNING record (`bounce_boot_next()`).
  - A tripped breaker also deletes a newer build's record that it names.

A newer record is still replaced or deleted when this build writes or ends the same session (a put, a session end, a replica teardown). This is deliberate: this build has then seen the session's current state, and keeping the stale record would bring back a session the user ended.

Testing: build and all CMocka suites pass. `bouncer_record_cmocka` covers the decode statuses and the span, the heartbeat codec (layout unchanged, untagged and corrupt tags), the restore rule against the heartbeat's writer, the breaker, and the boot record's next state. The bouncer-architecture skill (invariant 20) documents the rollback rules.

**Changed after review:**
- **A roll-forward no longer restores two sessions under one nick.** While the older build ran, the user it could not restore reconnected and got a second session, usually under the same nick, and the roll-forward brought both back as ghosts under that nick. The restore loop now builds no ghost whose nick is already held: the first record read keeps the nick, and the other is logged and stays on disk until its hold ends.
- The cleanup line counts what it deleted and the unreadable records.
- Newer-build records are reported in one line per start, not one per record.
- `bounce_restore_prepare()` and `bounce_db_restore()` themselves still have no unit test.

**Operators:** turning the bouncer off to break a crash loop now drops the sessions the breaker names at that start; before, they were dropped at the next start with the bouncer on. A lone bad-size or unknown-version record is now deleted at the next start. New log lines include the L_CRIT "deleting session ... (a v%u record, of a newer build)".

**Decided:**
- A session live when a newer build crashed, after which an older build ran, is expired at the roll-forward.
- A session whose nick another restored session holds is skipped, not restored under a fallback nick.

**Simplified after the second review:** the selection pass is taken back out (`bounce_restore_select()`, its candidate collection and logging, the eviction pass's rule for migrated records, and their CMocka cases: about 300 lines). Only the guard in the restore loop remains. What that gives up, each at worst a reconnect and rejoin:
- Which of two sessions under one nick comes back is decided by the order the records are read, not by which was active latest. A user may get back the pre-rollback session instead of the one used during the rollback.
- The session that loses is not deleted. It is skipped at each start until its hold ends, and it is not counted against `BOUNCER_MAX_SESSIONS` meanwhile.
- A migrated (v8 to v11) record that the guard skips is evicted with the unreadable ones if the eviction pass runs at that start.
- `BOUNCER_MAX_SESSIONS` is not applied at a restore, as before this PR. Lowering the cap and restarting does not drop sessions.

Debug build with no warnings; all CMocka suites pass. The rollback and roll-forward sequences were not re-run on a server after the cut.
