A REHASH whose configuration has an error used to discard everything after the error.

`rehash()` freed the running configuration, then parsed the new file and applied whatever came out, even when the parser had reported errors. What freed meant: the conf list, crules, denies, WebIRC, quarantines and DNSBL servers were dropped, and classes, listeners and IAuth were marked closing. What got lost depended on where the error was:
- A syntax error lost its block. In a Port block, that closed the listener.
- An error inside the Features block lost every feature after it.
- A missing include lost its contents.

Only a file that could not be read at all was refused (55b8ba9 / f4d0870).

**The fix: check the new file before discarding anything.**
- **A fresh `ircd -k` reads the new configuration first.** The running binary (`/proc/self/exe`, else `SPATH`) runs as `-k -d . -f <conf>` in a process of its own. It inherits none of the server's descriptors and starts in its own process group, with signal handlers reset. The wait is bounded at 10 s, after which the check is killed along with anything it started.
- **A configuration with errors abandons the rehash and changes nothing.** The CONFIG log gets every line the check printed, and operators get the first five. On the fork, the error flag is set, so GitSync restores its copy as it does for an unreadable file.
- **Anything but a clean pass abandons the rehash too.** If the check crashed, was killed, timed out after 10 s or could not be started, the rehash is abandoned with nothing changed and one notice saying how the check ended; what it printed, with that last line, goes to the CONFIG log. There is no distinction between signals, and no retry inside the rehash: rehash again to try again.
- **SIGCHLD ignored no longer defeats the check.** The kqueue engine (FreeBSD, macOS) ignores SIGCHLD, so the kernel reaped the check and it always counted as not run. SIGCHLD is now default while the check runs, and a check reaped elsewhere is never killed by pid.

**Why exec and not fork:** a fork of the running server shares its sockets, poll set and TLS state (and on the fork, the stores). A parse in the child reaches all of them. Examples: queued notices flushed onto client sockets, epoll changes, the Keycloak webhook listener, and feature callbacks writing the store. An audit of the parse path found more than a dozen such effects. A fresh `-k` is the boot environment that check-only mode was written for.

**Limits:**
- The server waits for the check: tens of milliseconds normally, 10 s at most. The child closes the server's descriptors with one call on Linux 5.9+, the BSDs and Solaris; elsewhere it closes them one by one, which takes longer the higher the descriptor limit.
- A fresh `-k` cannot report "Redefinition of server name/numeric", because that error needs the running values. A rehash that changes them passes the check and then fails in the real parse, as before.
- **A file that changes during the check abandons the rehash.** The check reads the file by name, while the parse reads the copy `rehash()` already opened. If the file changed in the meantime (rewritten in place, or another renamed over it), the rehash is abandoned with a notice; rehash again to apply it. Include files are not compared.
- Until #238 lands, each check also logs the bind failures of `-k` against the live listeners. #238 stops `-k` from opening listeners.

**Testing:** build and all CMocka suites pass. `conf_precheck_cmocka` covers:
- every way the check can end (an exit status, a fault, another signal), and what each result means
- its arguments
- the timeout, including a check that closes its output early
- a process left behind holding the output
- long output
- that the check inherits no descriptor
- SIGCHLD ignored

I also checked against a running server, started with a relative `-d`. After a second Port block was broken, a SIGHUP used to close that listener. Now the listener stays open, and the parse error is in the CONFIG log. A valid change still applies. With the file being appended to every few milliseconds through a SIGHUP, the rehash is abandoned with the notice, and the next quiet SIGHUP applies it.

**GitSync:** GitSync applies a commit only when the check passes. When its rehash is abandoned, for whatever reason (errors found, or a check that crashed, was killed, timed out or could not run, or a file that changed while it was checked), GitSync puts its file back (the backup, or no file if there was none) and tries the content again at the next sync. Nothing is refused: the check judges the whole configuration, so its errors need not be the commit's. No second rehash or re-check follows an abandon: the running configuration is still the one from before. A commit that stays broken is checked, and reported to operators, once per sync interval until it is fixed.

**Changed after review:**
- The check's child closed every descriptor number up to the hard limit, one `close()` each: 300 ms and more at a limit of 524288. It now uses `closefrom()` where configure finds it or on a BSD or Solaris (by platform macro, since the committed `configure` does not have the check), else Linux's `close_range()`, else the loop.

- `ircd -k` logs nothing to the server's files or syslog. A check no longer writes "Failed to read configuration file" at CRIT into the live logs. Checked with a real binary: the old one wrote the line to the configured log file, the new one writes nothing there and still prints the error.
- `pipe()` and `fork()` failures say why, and an exec failure names the binary.
- The check's exit is noticed with `waitid(WNOWAIT)`, and its process group is killed before it is reaped, so the group id cannot have been reused. After a timeout kill it is waited for at most a second.

- `conf_precheck_cmocka` covers the timeout result, a failed `fork()` (as a non-root user), and the descriptor close at a large limit (skipped where the hard limit cannot be raised). The `s_conf.c` and GitSync glue still has no unit test.

**Simplified after the design review:** the check has three results only: a clean pass, errors, or did not finish cleanly. Only a clean pass applies. Removed: the "did not run, go ahead" path, the re-check of a changed file, `conf_file_check()` and GitSync's second rehash (net 96 lines fewer).

**Decided:**
- The mechanism stays a child-process check. Staged parsing would be the ideal design some day.
- GitSync applies a commit only when the check passes; any other outcome puts the old file back and retries at the next sync, with no distinction between signals or between errors and a check that did not finish.

**Changed after the second review:**
- GitSync no longer refuses content after an abandoned rehash. Before, a valid commit was refused when ircd.conf had an error of its own, or an include was missing during the check, and it stayed refused after the fix until `GITSYNC force`. `conf_rehash_abandoned()` is now a yes or no.
- A check that crashes leaves no core file: it runs with a core limit of 0.
- The parent calls `setpgid()` as well as the child, so the group exists before a timeout can kill it.
- `precheck_binary()` only picks `/proc/self/exe` or `SPATH`. The check's `argv[0]` is what is executed, `conf_precheck_run()` loses its `argv0` argument, and the notice says `ircd -k` (about 30 lines fewer).
- `conf_precheck_cmocka` checks the core limit.
- Not run on a live server this round: the GitSync change removes one branch and was built and unit-tested only.

**Deploy:** every REHASH and GitSync apply now runs `ircd -k`, so run the new binary's `-k` against the live ircd.conf before upgrading: an error tolerated today would block every REHASH and hold back every commit. #238 is a co-requisite: without it the check binds every Port, and a client reaching a newly added one during the check is reset.
