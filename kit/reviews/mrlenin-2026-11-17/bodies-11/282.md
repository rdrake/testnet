OPER and SETHOST check the password off the main thread (`ircd_crypt_verify_async()`) and return straight away. The client's next lines were then parsed immediately, so their replies went out before the 381/464 (or the SETHOST answer). A client that reads replies in order took the reply to its next command for the OPER's, and the OPER's for the next one's. In irctest, the OPER, WHO, WHOIS, INFO and KILL tests failed a different few on every run because of this. Setting `THREAD_POOL_SIZE` to 0 doesn't avoid it, because 0 means the default size.

### What changes

- **The wait.** While an OPER or SETHOST check is pending (`IsOperPending()` / `IsSetHostPending()`), `read_packet()` leaves the client's queued lines unparsed (`input_awaits_answer()`). The socket is still read, and the lines wait in order.
- **The resume.** The check's callback calls `client_input_resume()`. The queue is processed at the event loop's next timer pass, after the answer has gone out.
- **No state of its own.** The wait lasts exactly while the check is pending. It has no timeout, no start time and no event, and it does not change the receive allowance. It is checked before the bouncer orphan hold.
- **Docs.** The bouncer-architecture skill (invariant 23) describes the wait.

The whole change is 63 lines in seven files.

### Limits

- **A check that never answers.** Nothing ends the wait if a worker is stuck or ircd.conf sets an absurd hash cost: that client's lines wait until it pings out. There is no backstop timer and no log line for it.
- **WEBIRC is not covered**, and does not need to be: a successful check answers nothing, a failed one disconnects, and registration already waits for it.
- **Bouncer revive and hold** already cleared both pending flags before this PR; nothing is added there.

### Not in this PR

The answer itself still arrives at the event loop's next wake-up, which can take up to about a second on an idle server. The thread pool's completion pipe isn't registered with any engine, so `thread_pool_poll()` only runs at the end of a pass. The lines behind the OPER now wait that long too, but in order. #296 registers the pipe, which shortens the wait to the hash time.

### Tests

- **CMocka `oper_verify_cmocka` and `sethost_verify_cmocka`:** an answer resumes the client's input, and a result meant for another connection doesn't.
- **The whole CMocka suite passes** after a clean build.
- **irctest** (Nefarious controller): the OPER, WHO, WHOIS, INFO and KILL tests pass in three runs in a row. The full runs with and without X3 services show no new failures.
