The `PERSISTENCE` command and the `draft/persistence` capability carried two things:
- the specification's surface: STATUS, GET and SET;
- the fork's own extras: ATTACH, DETACH, LIST, PROFILE and REPLAY.

Two names on the wire were also defined nowhere:
- A held session's restored channel state came in a batch typed `draft/persistence`. The persistence draft defines no batch type.
- The server advertised a `draft/bouncer` capability that nothing read.

This PR follows the agreed direction:
- **New capability `evilnet.github.io/persistence`.** It carries the extras, and its value now holds the tokens (`attach,detach,list,attach-cursor`). `draft/persistence` has no value, because the spec defines none. STATUS, GET and SET stay on `draft/persistence`. A refused SET sends a WARN and the unchanged STATUS, as the spec says. Two deviations remain: SET answers with a `PERSISTENCE SET ON|OFF|DEFAULT` line before the STATUS (Seance shows it), and an unknown subcommand gets a FAIL, where the spec says a server SHOULD ignore it.
- **The vendor capability announces the extras; it does not gate them.** Every connection reaches ATTACH, DETACH, LIST, PROFILE and REPLAY, with or without a capability (see "Changed after review").
- **The restore batch is typed `evilnet.github.io/persistence`** for a connection that negotiated the vendor capability.
- **`draft/bouncer` is gone.** `CAP_draft_bouncer` remains as an obsolete setting that nothing reads, so existing configurations still load.

**Clients:** evilnet/seance#327, an unmerged draft, requests both capabilities, reads `attach-cursor` from either one's value, and accepts either batch type. Seance develop requests only `draft/persistence`, reads `attach-cursor` from its value, and accepts only the `draft/persistence` batch; it sees no change only on a network that turns `PERSISTENCE_DRAFT_EXTRAS` on, and the flag is now off by default. Seance's side is tracked in evilnet/seance#333. The testnet test that expects `draft/bouncer` to be advertised needs updating. `persistence-batch.test.ts` passes only with the flag on, since its clients request `draft/persistence` only; it needs the flag set in the testnet config or its clients moved to the vendor capability.

**Testing:** build and all CMocka suites pass. I also checked on a running server:
- CAP LS shows `evilnet.github.io/persistence=attach,detach,list,attach-cursor` and a bare `draft/persistence`.
- `PERSISTENCE LIST` reaches the subcommand with or without a capability, whatever `PERSISTENCE_DRAFT_EXTRAS` is set to.

**Changed after review:** while `PERSISTENCE_DRAFT_EXTRAS` is TRUE, a client written against the old names sees no change:
- a connection without the vendor capability gets the restore batch typed `draft/persistence`;
- `draft/persistence` carries the extras' value too, where such clients read `attach-cursor` (set at start and when the flag changes);
- the extras are not gated at all (below).

With the flag FALSE, `draft/persistence` has no value and every restore batch has the vendor type.

- **The extras are no longer gated.** ATTACH, DETACH, LIST, PROFILE and REPLAY work on any connection, with or without `evilnet.github.io/persistence` and whatever `PERSISTENCE_DRAFT_EXTRAS` is set to. ibutsu pointed out that the draft says implementations SHOULD ignore unrecognized subcommands (so the command is meant to be extended), and that a gate stops a bouncer user on a client without the cap from adjusting auto-replay. The gate also protected nothing: each extra requires the account (ATTACH and LIST also accept a completed SASL exchange before registration) and acts only on that account's own sessions and settings, and the spec's own SET needs no cap. The vendor cap now only announces the extras (its token value) and names the restore batch type; `PERSISTENCE_DRAFT_EXTRAS` only keeps the old names for clients written against them (the value on `draft/persistence` and the `draft/persistence` restore batch type). A subcommand the server does not have is still answered with `FAIL PERSISTENCE INVALID_PARAMETERS`. New `persistence_cmocka` covers the dispatch. `readme.features` says this, and that the account metadata keys (`draft/persistence/hold`, `.../auto-replay`, `.../profile/*`) keep their names, since renaming them would migrate the stores and the S2S wire.

**Mixed builds:** nothing changes on the S2S wire or on disk. On rollback, a config that sets `CAP_evilnet_persistence` or `PERSISTENCE_DRAFT_EXTRAS` gets a harmless "Unknown feature" CONFIG error.

**Decided:** nefarious2 makes its transitions without waiting for its clients. `PERSISTENCE_DRAFT_EXTRAS` defaults to FALSE, so by default the server behaves as the final state: `draft/persistence` has no value, a restore is batched only for a connection with `evilnet.github.io/persistence`, and SET is answered with its STATUS alone. A network whose clients still need the old names turns it on. `readme.features` says so.

**Decided:** the capability is named `evilnet.github.io/persistence`. Vendor-specific capability names "are prefixed by a valid DNS domain name" (`extensions/capability-negotiation.md:510`), which `evilnet/<name>` is not.

**Decided:** the extras stay `PERSISTENCE` subcommands: the draft says "Implementations SHOULD ignore unrecognized subcommands, to be compatible with future extensions of this specification" (ibutsu). **Decided:** cap-less use of the extras does not end, with this change or when the flag goes FALSE (ibutsu: a gate "blocks bouncer users without the CAP from adjusting the auto-replay").

**Changed after review (cap-gating):** ibutsu's rule of thumb is that anything the server sends unsolicited that the client may not understand must be cap-gated. The extras only answer the client's own commands, so leaving them ungated fits it. What the server sends on its own now follows it:
- The restore batch is wrapped only for a connection that negotiated `evilnet.github.io/persistence` (vendor type), or, while `PERSISTENCE_DRAFT_EXTRAS` is on, any `batch` client (old `draft/persistence` type, as before). Otherwise the same JOIN/TOPIC/NAMES lines go out unwrapped, so with the flag off no client gets a batch type it could not know, and with `CAP_evilnet_persistence` off nobody gets the vendor type.
- The `PERSISTENCE SET <state>` line before a SET's STATUS (a deviation from the spec, which answers with the STATUS alone) goes only to a connection with the vendor cap, or to any while the flag is on.
- The file header, the command's help string and `readme.features` (what the cap value lists) are brought up to date. `persistence_cmocka` checks the SET line.

**Changed after a second review:** the restore batch type is chosen by `persistence_restore_batch_type()`, unit-tested in `persistence_cmocka`.

**Changed after review (re-evaluation):** The value re-announce is back without the three hand-written hooks. `send_cap_notify()` given no value now sends the capability's stored value, the one CAP LS 302 lists, so the generic notify hook announces `evilnet.github.io/persistence` and `draft/persistence` with the extras' value when they are switched on. `PERSISTENCE_DRAFT_EXTRAS` sends `CAP NEW draft/persistence` with the new value (or the bare name once it has none) while the capability is offered. A side effect: `CAP NEW draft/metadata-2` carries its value too. Checked on a scratch server with `SET` and with `REHASH`; this branch has no CMocka harness for `m_cap.c` (the one in #283 can take a case once both are in).

**Changed after the second review:**
- The automatic replay's outer `evilnet.github.io/bouncer-replay` batch follows the restore batch's rule: it goes to a connection that negotiated `evilnet.github.io/persistence`, and to any other only while `PERSISTENCE_DRAFT_EXTRAS` is on. It was gated on `batch` alone. The inner chathistory batches are unchanged.
- `readme.features` says what a running server sends when `PERSISTENCE_DRAFT_EXTRAS` changes: going to FALSE is a bare `CAP NEW :draft/persistence`, since CAP has no form for a removed value and a DEL followed by a NEW would cancel the capability for every client. A client may keep the old `attach-cursor` until it reconnects.
- Debug build with no warnings; all CMocka suites pass. Not re-run on a live server.

**Not changed:** the runtime re-announce on a flag change and `cap_stored_value()` stay as they are; the second can become a one-line call to #249's `cap_named()` once both are in.

**Needs #249 in first.** Alone, a pre-302 cap-notify client is sent the stored values and a NEW for a capability it already has; with #249 it gets nothing on the flag toggles.

**Deploy:** with the flag at its default FALSE, a client that requests only `draft/persistence` (Seance before evilnet/seance#327) gets restored JOINs unwrapped, no outer replay batch and no `attach-cursor`. A network still serving such clients sets `PERSISTENCE_DRAFT_EXTRAS = TRUE` until they are updated.
