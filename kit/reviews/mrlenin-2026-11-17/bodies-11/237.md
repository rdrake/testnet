`main()` started the thread pool and async logging right after `feature_init()`, which is before `init_conf()` reads ircd.conf. Both therefore always ran with their compiled defaults:

- A configured `THREAD_POOL_SIZE` was ignored (4 workers whatever it said).
- `"ASYNC_LOGGING" = "TRUE"` never started the writer thread.
- A configuration check (`ircd -k`) started the four workers as well.

Turning this code on exposed bugs in it that had never run, so the PR fixes those too.

**Startup**

- **Both now start after `init_conf()` and after the PID file is locked.** The configured values are in force, and a configuration check (or a second copy that was refused the PID file) starts no thread.
- **Both settings are read once, at startup.** A REHASH or `SET` that changes either one logs that the change takes effect at the next restart (one notify callback, `feature_notify_at_restart()`, for the two; quiet while ircd.conf is first read and on a REHASH that changes neither). No thread starts or stops on a running server.
- **Startup logs that async logging is on**, and that a crash loses the lines still queued.
- **`log_async_init()` sets `running` only once the writer thread exists.**
- **`THREAD_POOL_SIZE` is capped at 64 with a warning.**
- **`readme.features` documents both settings.**

**The async writer**

- **A full queue waits and keeps the order.** The old full-queue path waited once and then wrote into the ring whether or not there was room, which could overwrite the entry the writer was on and make the ring look empty. A line that finds the queue full now waits for the writer to free a slot and rechecks after every wake. It is never written ahead of older queued lines, and there is no direct-write fallback. A shutdown wakes the wait, and the caller then writes the line itself.
- **The `running` flag is read and written atomically.**
- **A queue entry holds the whole line `log_vwrite()` builds**, so a long line is not cut shorter when queued; a compile-time check keeps the two sizes in step. A line that is cut anyway still ends with its newline.
- **Syslog gets only the message.** Queued lines went to syslog with the file's timestamp and a trailing newline. Each entry now records where its message starts.
- **The writer stops through `log_async_shutdown()`**, which writes what is queued first. An `ssl_init()` failure after startup stops the writers before `exit(1)`, so what it logged is written.

**The thread pool**

- **A failed `thread_pool_init()` no longer leaves `signal_pipe[]` naming closed descriptors.** `thread_pool_poll()` read those closed (or reused) descriptors. The pipe is -1 until init, and again after a failed init.
- **The failed-init shutdown clears `running` under `task_mutex`.** Before, a worker between its check and its wait could miss the broadcast and hang the join.
- **`pthread_create()` errors are reported from its return value**, not from `errno`.
- **A pool that cannot start all its threads does not start.** It logs the failure, and the password checks run on the main loop as they do without a pool.

**Tests**

`log_async_cmocka` (10 cases) covers:
- a cut line keeping its newline, also behind a full queue
- syslog getting the line without the file's stamp
- a spurious wakeup while the ring is full not being taken as room
- a line past a full queue written once, after every line logged before it
- flush waiting for the write in flight
- closing or destroying a log file draining its queued lines first
- shutdown writing the queue, and no log reopening after it

The cases do not depend on running order. All CMocka suites pass, 50 repeated runs of `log_async_cmocka` included.

Boot checks: `THREAD_POOL_SIZE` 7 with `ASYNC_LOGGING` gives 12 threads (8 before). Pool 2 without it gives 6. 500 is capped at 64 workers. A REHASH that changes either key logs the restart notice and starts no thread, and `ircd -k` makes no `clone()` call.

**Not in this PR**

- Switching the log writer on or off on a running server. Before this branch the writer also started only at startup; an ordered switch needs an accepting state and a drain wait in the queue, in files #296 also changes.
- Keeping a partly started pool.
- Logging from worker threads in DEBUGMODE builds has concurrency gaps that need a redesign, so that goes in a separate issue. Release builds do not log from pool workers, except on the out-of-memory path, where `outofmemory()` runs `server_restart()` on the worker.

**Operators**

- An ircd.conf that already sets either key changes behaviour on upgrade: `THREAD_POOL_SIZE` now takes effect, and `ASYNC_LOGGING` adds a thread and a ring of about 8.7 MB.
- After a REHASH or `SET` of either key, `GET` shows the new value while the old one is still in force until the restart; the log line is the only notice.
- With the ring full, a line waits behind the writer's `write()`, so a slow log target (NFS, a backed-up syslog) blocks the caller as synchronous logging does.
- Nothing changes on the wire or on disk, so a rollback is clean.
