A profile's settings are stored under `draft/persistence/profile/<name>/<setting>`. With a name of up to `PERSISTENCE_PROFILE_NAME_MAX` (32) characters, that key is often 64 bytes or more. `metadata_account_list()`, which every profile walk used, cannot hold a key that long and skips it. So:
- PERSISTENCE PROFILE DELETE left those settings in the store, on every fork server, since profiles replicate.
- RENAME did not copy them, and did not repoint a long-named child's parent.
- DELETE did not see a long-named child, so it deleted a profile others still inherit from.
- LIST did not show a profile with a long name.

**The fix:** the walks collect the account's live profile rows with `metadata_account_foreach_version()`, which visits keys up to 159 bytes, and act on them after the walk as before. Keys are now held to the wire's 127 bytes (see below), so every key that can be stored is reached. Tombstones are skipped and store order is kept.

The name is also folded before it is matched. The store folds every metadata key to lower case, so a profile made as `Work` is stored under `.../profile/work/`. DELETE and RENAME of `Work` built their match prefix from the name as typed and matched no row: DELETE reported success and left everything, and RENAME copied nothing.

**Testing:** new CMocka suite `persistence_profile_cmocka`. It runs over an in-memory store whose `metadata_account_list()` skips long keys the way the real one does. The store folds keys like the real one. Its six cases failed before the change and pass after (the folding case was added after review and failed before its fix); all other suites pass.

**Changed after review:**
- PROFILE SET refuses a key the S2S wire would refuse (`md_wire_key_valid()`, 127 bytes), with `FAIL ... INVALID_PARAMETERS`. Every stored key is then walked and replicated; before, a key over 127 bytes stayed on one server, and one of 160 bytes or more was skipped by the walk and came back after a later CREATE. Unsetting a key still works. Rows already stored above 159 bytes stay unreachable.
- RENAME to a longer name that would push a key past the limit is refused before any of the profile's rows is copied or changed. Leftover rows an older build left under the new name are cleared first, so a refused RENAME may already have removed those.
- CREATE removes every row under the name before it writes the parent. This covers rows an older server's RENAME or DELETE of a 29- or 30-character name left behind.
- The name is folded with `db_casefold_bytes()`, the store's own fold.
- `persistence_profile_cmocka` adds SET at 127 and 128 bytes, a RENAME that would grow a key past the limit, and CREATE over leftover rows; all three fail without the change. Its fake walk now skips keys of 160 bytes or more, as the real one does, but it restates `metadata_account_foreach_version()`, so the real walk's buffer is not exercised.

**Changed after review (re-evaluation):** CREATE again removes rows an older build left under the name (the review's item 2: the channels of a deleted profile came back in a new profile of the same name), and a RENAME to such a name does the same. DELETE's loop became `delete_profile_rows()`, which the three share, so it costs a few lines and the one walk DELETE already makes. CMocka: `create_and_rename_clear_leftover_rows`.
