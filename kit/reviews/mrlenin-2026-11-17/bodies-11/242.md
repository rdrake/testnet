Three parsing fixes in SEARCH and timestamp handling.

- **SEARCH's selector budget counted the selectors alone.** `SEARCH_SEL_MAX` is 380 bytes. A search in a channel federates, and its `CH Q S` line also carries the channel name and the fixed fields. A name of about 200 bytes with a long `text=` passed the check, and the line was cut on its way out. The check now counts the whole federated line (`SEARCH_FED_FIXED` plus the name plus the selectors) against the 510 bytes of a P10 line.
- **The `CH Q S` responder cut `from=` before unescaping it.** It copied the still-escaped value into the nick-sized `ssm.from` and unescaped it there, so a nick with many `\` escapes was cut first. It now unescapes in place, then copies. A nick that is still too long is answered with no rows (`E <reqid> 0`), as the requester's own check would have refused it. Before, it was cut to a shorter nick that could match.
- **`history_iso_to_unix()` accepted anything after the seconds and the fraction.**
  - `+02:00` was ignored, so the time was read as UTC and came out wrong by the offset. `Zjunk` passed too. Now only `Z` or the end of the string may follow.
  - The client reference check refuses a timestamp that does not convert. Before, the stores fell back to reading such a timestamp as unix time and built keys from the ISO text.
  - MARKREAD refuses a timestamp too long for its copy. It used to cut it, offset and all, before the conversion could see it.

Testing: build and all CMocka suites pass. On a running server:
- BEFORE with `...000+02:00` or `...000Zjunk` returned history before and now gets `FAIL ... INVALID_PARAMS`.
- `...000Z` still works.
- SEARCH in a 191-byte channel with a 250-byte `text=` now gets `FAIL SEARCH INVALID_PARAMS text`, and the same text in `#j` is still searched. That line measured 498 bytes, so it was not cut before either; it is refused because `SEARCH_FED_FIXED` counts every field at its maximum. A text that escapes long does get cut on the old build: `q`, 170 spaces and `NOPE` in a 192-byte channel made a 510-byte line, and the peer returned a row without the text. That query is refused now too. The check runs whenever `in=` is a channel, also on a single server.

**Changed after review:**
- An older requester passes a client's timestamp through on `CH Q` as it came, `+00:00` or a lowercase `z` included. The store walks took any ISO text that did not convert as if it were already unix time and keyed the walk from it, so BEFORE returned the wrong page and AFTER only the newest rows. `history_ref_to_unix()` now accepts only an ISO time that converts or a value already in `sec.mmm` form, and every walk (before, after, latest, latest-after, around, between) refuses anything else. The responder answers `E <reqid> 0 U` for a TIMESTAMP reference it cannot read, so the requester withholds the end tag.
- `history_iso_to_unix()` moved to `history_record.c` with the new helper, so `history_cmocka` links the real converters.
- A client timestamp is now taken only in the spec's form, `YYYY-MM-DDThh:mm:ss.sssZ` (chathistory and read-marker: "MUST have the format `timestamp=YYYY-MM-DDThh:mm:ss.sssZ`, as in the server-time extension"): 24 characters, exactly three fractional digits, uppercase `T` and `Z`, fields in range, a day that exists. Seconds may be 60, the leap second server-time's own example shows. Every client entry point goes through `history_iso_to_unix()` (CHATHISTORY references, SEARCH `after=`/`before=`, MARKREAD), so anything else gets the refusal each already sends. Unix `sec.mmm` references between servers are unchanged. `history_cmocka` checks the spec form and a leap second are accepted, and that an offset, a missing `Z` or fraction, a fraction of 1, 4 or 6 digits, lowercase `t`/`z`, a missing `T`, a short field, a sign or space in a field, seconds 61, hour 24, month 13, 31 November and 29 February 2026 are refused.

**Decided:** an explicit zero offset (`+00:00`, what Python's `datetime.isoformat()` gives for an aware UTC time) stays refused. The chathistory spec says a `timestamp` parameter MUST have the format `timestamp=YYYY-MM-DDThh:mm:ss.sssZ` (`extensions/chathistory.md:67`), so such a client is out of spec and gets `FAIL ... INVALID_PARAMS`.

**Changed after a second review:** Between servers the responder still reads an ISO time leniently (no fraction or a fraction of any length, an optional Z). An origin on an older build forwards the client's text as its own parser took it, and those forms worked end to end before. Only an offset, junk or a date that does not exist gets `E <reqid> 0 U`. A time before 1970 is refused everywhere (it went negative and became a far-future key). With CHATHISTORY_STRICT_TIMESTAMPS off, a unix reference no walk can key from, such as `1700000000.`, now gets INVALID_PARAMS rather than MESSAGE_ERROR.

**Unix timestamps from clients:** `CHATHISTORY_STRICT_TIMESTAMPS` now defaults to TRUE, so CHATHISTORY and TARGETS refuse a client's unix `sec[.mmm]` reference by default, as MARKREAD and SEARCH always did. The spec has only the ISO form. An operator who needs the old behaviour for a client can set the feature FALSE. Servers still exchange unix references between themselves. Built and all CMocka suites pass; the default was not exercised on a live server.
