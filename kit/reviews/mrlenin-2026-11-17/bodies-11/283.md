A `CAP REQ` for a capability that `CAP LS` doesn't list was ACKed. For example, `draft/account-registration` with its feature off, `sasl` with no SASL server, or `draft/authtoken` with no service. The capability-negotiation spec says the requested set "must be accepted as a whole, or rejected entirely", and a capability that is not on offer cannot be accepted.

### What changes

- **One rule.** `cap_offered()` (capab.h, pure) says whether LS offers a capability: not hidden, feature on, what it needs is up, and the client's CAP version is high enough. m_cap.c's `cap_offered_at()` / `cap_offered_to()` gather those facts.
- **LS.** `send_caplist()` uses the rule. LS output is the same as before.
- **REQ.** If any entry of a `CAP REQ` is refused, the whole REQ is NAKed, as the spec requires. `cap_req()` NAKs an entry that `cap_req_refused()` refuses:
  - adding a capability that is prohibited, or not offered and not already held;
  - removing a sticky one.
  
  Removing a capability is never refused for not being offered. Re-requesting one the connection already holds isn't either, so a client can drop a capability the server stopped offering, or repeat its full set.
- **CAP NEW.** `send_cap_notify()` and the rehash batch send NEW only for a capability that is offered, so a client is never told of one its REQ would then NAK. Before:
  - services quitting while IAuth claimed SASL with no mechanisms sent `CAP NEW sasl`;
  - `sasl` and `draft/webpush` got CAP NEW with their feature switched off.
  
  The batch takes sasl's mechanism list when it is flushed, not when it was queued, and `CAP NEW sasl` from `send_cap_notify()` always carries the list CAP LS gives (`cap_sasl_mechanisms()`).
- **CAP DEL.** DEL, immediate or batched, goes to every cap-notify client, and takes the capability from each client it goes to, with its dependents, as a `CAP REQ -cap` does ("servers MUST cancel any capability-specific behavior for a client after sending the CAP DEL message"). Before, `CAP LIST` still showed it and a new REQ was ACKed while it was not offered. A client that was never sent the DEL (no cap-notify, before 302) keeps what it holds.
- **cap-notify.** A CAP 302 client's REQ for `cap-notify` is always ACKed, whatever `CAP_cap_notify` says ("Servers MUST accept and CAP ACK the request"); that client is sent NEW and DEL anyway. An older client's request follows the feature.
- **Feature switches.** `CAP_sasl` and `CAP_draft_webpush` now send CAP NEW or DEL when switched, like the other capability features. Before, neither had a notifier, so switching them sent nothing.
- **draft/webpush** is offered only with libkc's HTTP transport, which is set up at boot. Switching the feature on later used to list it in LS with nothing to deliver pushes.

### Not in this PR

`sasl_mark_unhealthy()` and the services-quit path send `CAP DEL sasl` even when another SASL tier keeps it offered. That was already so and needs its own change.

**Changed after a further review pass:**
- A CAP DEL clears a capability only from a client that CAP LS no longer offers it to. Two cases it had cleared wrongly: switching `CAP_cap_notify` off (a 302 client is still offered `cap-notify` and still notified), and services leaving while IAuth keeps SASL up, which sends DEL then NEW and left the client without `sasl`.
- A rehash that changes more capabilities than one line holds sent one line cut at 510 bytes. NEW and DEL now go out in as many lines as it takes, cut between names. `cap_handlers_cmocka` covers both.

**Known limits:**
- Switching `CAP_cap_notify` off still sends 302 clients a `CAP DEL :cap-notify` that changes nothing for them.
- Withdrawing `batch` or `draft/multiline` while a client has a multiline batch open discards the batch; fragments the client sent before it saw the DEL are then delivered as ordinary messages. The same happens today when a client drops the capability itself.
- A client still registering (before `CAP END`) is not sent NEW or DEL, as before.
