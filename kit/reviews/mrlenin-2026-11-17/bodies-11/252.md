`SEARCH text=foo in=#chan` asks the other storage servers too, but `SEARCH text=foo` with no `in=` searched only this server's store. A bouncer device attached to a different server from its primary therefore missed rows that only another server holds, such as messages from times when its own server had no member in the channel.

**The fix:** SEARCH without `in=` now fans out per channel.
- Each channel the requester is in becomes one federated request, when any other storage server is linked.
- Each request is part of one aggregate. When the last part comes in, the aggregate sends a single `soju.im/search` batch: the newest `limit` rows across all channels, under the SEARCH line's label.

**Limits**, since each part asks every storage server for its own scan and holds a federation slot until it answers:
- At most 8 channels federate per search (`SEARCH_FED_PARTS_MAX`).
- One client has at most `SEARCH_FED_PARTS_MAX` (8) parts in flight across all its searches. A search that cannot have the parts it would get on an idle server is refused with `FAIL SEARCH TEMPORARILY_UNAVAILABLE` and nothing is scanned; it is not answered from this store alone.
- A search never leaves fewer than a quarter of the federation slots free (`SEARCH_FED_RESERVE`).
- Channels past those bounds are searched on this server only, as before. Which 8 channels federate depends on membership order.

Lifetime: a part freed without completing still counts as finished. A bouncer revive drops the aggregate's client, just as it does for a single request.

`in=` searches are unchanged, except for the long-line rule below.

**Testing:** build and all CMocka suites pass. I also checked on two linked servers:
- A message sent on server B in a channel where A had no member at the time is now found by a no-`in` SEARCH from A. Before, it was missing.
- A's own rows from another channel are in the same batch.
- The label is on the batch.

**Added after review:** a SEARCH whose `CH Q S` line would pass 510 bytes is no longer federated. With a long channel name and a long `text=`, msgq cut the line, so the responder searched for a shorter text than the user asked for and returned rows that did not match. The line is now measured as it will be sent. (The first version of this answered a query that cannot fit from this server's store only; see below.) I checked this on two linked servers with a 150-character channel and a 325-byte `text=` that the stored message does not contain: the old build returned the message, and the new one returns nothing. A short query still federates.

**Changed after review:**
- A query whose `CH Q S` line cannot fit is refused with `FAIL SEARCH INVALID_PARAMS`: with `in=`, when that channel's line cannot fit, and without it, when any searched channel's cannot. This applies whether or not another storage server is linked, so a search answers alike on one server and on many, as #242 does for an over-long `in=` line. Before, the query was answered from this server only, without an error.
- The aggregate's bookkeeping moved to `chathistory_merge.c`, which has no store: `hm_keep_newest()` and `hm_search_agg`. CMocka covers the sort and trim, the hold until every channel is started, a part freed unfinished, the newest `limit` across parts, and an empty search. There is still no linked-pair Vitest case.

**Cost:** each part asks every storage peer for a full `SEARCH_SCAN_MAX` scan in its main loop. In the review's run, a no-`in` SEARCH over 8 channels of 50 000 rows kept the peer busy about 2.1 s, against about 0.3 s for one `in=` search.

**Decided:** a no-`in` SEARCH federates up to 8 of the requester's channels. The scan cost on the peers is moved off their main loop in #296.

**Changed after review (re-evaluation):** a SEARCH whose `CH Q S` line cannot fit one P10 line is refused again with `FAIL SEARCH INVALID_PARAMS`, for `in=` when that channel's line cannot fit and without `in=` when the line of any channel it would search cannot, whether or not another store is linked. Without the refusal that channel was answered from this server's store alone, with no error (the review's item 1). The one-search-in-flight-per-client rule stays removed: it answered a second search from this server only, the same silent loss, and the part limit and slot reserve already bound what a search takes. Checked on a scratch server: a 190-character channel with a 270-character text is refused in both forms; shorter queries and the same text after parting the long channel answer as before.

**Changed after the third review:**
- One client could take 48 of the 64 federation slots with a burst of searches, after which its own and other users' searches were silently answered from this store alone. A client's parts in flight now count against `SEARCH_FED_PARTS_MAX`, and a search that cannot get its parts is refused (above). Run on two linked servers, a client in 8 channels sending seven `SEARCH` lines in one write: the first is answered, the next four get `FAIL SEARCH TEMPORARILY_UNAVAILABLE * :Too many searches in progress, try again shortly`, and the last two, parsed after the first has finished, are answered. A search sent afterwards is answered in full.
- The line-length probe uses the widest request id the search's parts can take, so a counter gaining a digit mid-search cannot fail a line that passed the check.
- Debug build with no warnings; all CMocka suites pass.

**Presence filter (801ac5c5):** a page can come back short. A responder cuts to `limit` before this server applies the requester's presence filter, and SEARCH has no partial marker, so rows the filter removes are not replaced. There is still no two-server test in the tree for the filter; it was checked by the runs in the review.
