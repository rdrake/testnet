A bouncer device's NICK is a request to its primary's server (BX W). The device's server remembers the pending request in `cli_nickask_ts`, so a late answer can be told apart from a fresh one. Any 432, 433, 437 or 438 delivered to the device cleared that memory. So a refusal of an earlier request cancelled the next one: with `NICK x1` then `NICK x2` inside one round trip, x1's refusal cleared x2's request. Normally that does no harm: x2's answer reaches the device whatever the pending state says. It matters when the device is promoted to primary while x2 is in flight. Then x2's answer comes back as a return, was dropped as "not its last request", and the device stayed on its old nick with no word about x2.

**The fix:** a refusal numeric clears the pending request only when the nick it refuses is the nick asked for last. That nick is the first word of `parv[2]`, which holds the rest of the numeric's line. The compare is exact: the refusal echoes the nick as it was asked, so `NICK X2` then `NICK x2` are two requests, and a refusal of the first does not answer the second. 437 names a channel, not the nick, so it no longer clears anything; its request lapses at `NICK_ASK_RETURN_WINDOW` like any other unanswered one.

**Testing:** new CMocka suite `nickask_cmocka` runs `do_numeric()` on:
- 433, 432 and 438 for the asked nick: the request is cleared;
- an earlier, a longer, a shorter and a differently cased nick: the request is kept;
- 437: the request is kept.

Its first case also caught a bug in an earlier version of this change, which compared against the whole rest of the line and so never matched. All suites pass.

**Changed after review:** the commits are squashed into one that builds, the test helper sizes its copy from the field, and the commit message states the promote condition above.

**Limit:** the same nick asked twice, with both requests in flight, cannot be told apart. The first refusal clears the second's state, and the second's return after a promote is still dropped.
