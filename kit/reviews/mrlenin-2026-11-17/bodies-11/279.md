Setting `"LOG" = "local4"` in the Features block never takes effect. The server runs with the USER facility from startup, and stays on it after a REHASH. There are two inherited bugs here, one hiding the other:

- **`log_feature_mark()` resets in the wrong case.** It resets the default facility when the LOG feature is *marked*, that is, when the configuration has just set it. The test is inverted. The unmarked case, a configuration that no longer sets the facility, is the one that should go back to the default.
- **A subsystem line clears the mark.** A LOG line naming a subsystem (`"LOG" = "SYSTEM" "FACILITY" "local5"`) makes `feature_log_set()` return 0. `feature_set()` then falls through from FEAT_NONE into FEAT_INT, which reads `SYSTEM` as a number and clears the mark. So a default facility followed by any subsystem line was kept, by accident, while one on its own was reset.

**The fix:**
- The facility is reset only when it is unmarked.
- A set handler that returns 0 no longer falls through, and leaves the mark alone. LOG and RANDOM_SEED are the FEAT_NONE features. RANDOM_SEED returns 0 only on its missing-value error, so the new `break` leaves its behaviour unchanged.

**Testing:** checked as an oper with `GET LOG` on three configurations: the default facility only, the default facility plus a subsystem facility, and neither.

| Build | Facility only | Facility + subsystem | Neither |
|---|---|---|---|
| Before | USER | LOCAL4 | USER |
| After | LOCAL4 | LOCAL4 | USER |

These results hold both at startup and after REHASH. Dropping the line and rehashing goes back to USER, and putting it back gives LOCAL4. There is no CMocka suite for `ircd_features.c`.


This bug comes from ircu, and the same fix is opened against ircv3.2-upgrade separately.

#269 keeps the FEAT_NONE fall-through because of this bug, as #268 does on ircv3.2-upgrade. Whichever of the two lands second should drop that special case (the `(feat->flags & FEAT_MASK) != FEAT_INT` branch) and its comment. If the conflict is resolved toward #269 instead, a default facility followed by a subsystem LOG line goes back to USER at every boot and REHASH.

**Added after review:**
- A refused default facility now keeps the running one. With `"LOG" = "LOCAL9"` (no such facility) in the file, a REHASH used to put the facility back to USER, because the refusal left LOG unmarked. It is now marked, the same way a refused integer or boolean value is (#268/#269). I checked it as an oper with GET LOG: LOCAL4, then a REHASH with LOCAL9, then a REHASH with LOCAL4 again. Before the fix this gave LOCAL4, USER, LOCAL4; after it, LOCAL4 throughout. An operator's refused `SET LOG` changes nothing, as before.
- Behaviour change: a facility set at runtime with `SET LOG <facility>` now goes back to the file's value (or USER) at REHASH, like any other feature. Before, it survived a REHASH whenever the file had a subsystem LOG line, by the accident described above.
- A refused default facility is marked only when it leaves a facility other than USER running. Before, a refused `"LOG" = "LOCAL9"` at first boot was marked while USER stayed in effect, so `STATS f` listed `F LOG USER` as a configured line. Checked as an oper with GET LOG and STATS f, booting with LOCAL9, with LOCAL5, and rehashing between the two in both directions. Facilities are unchanged from before in every case; the only difference is that the `F LOG USER` line no longer appears.
- The source comment no longer says every refused feature value is kept. On this base a refused boolean, and a refused LOG subsystem value, still go back to their defaults at REHASH.

**Changed after review:** the three commits are squashed into one, so no in-between state can be bisected to. The commit message also says that a runtime `SET LOG <facility>` goes back to the file's value at REHASH. The tree is unchanged.
