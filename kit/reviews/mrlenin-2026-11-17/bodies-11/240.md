Federated CHATHISTORY page queries misread msgids that start with a digit as timestamps.

A msgid begins with its server's numnick (`generate_msgid()`), and the numnick digits 0-9 are values 52-61. Every server with a numeric from 3328 to 3967 therefore mints msgids that start with a digit. The requester put the client's reference on the `CH Q B/A/R/W` line bare, and the responder's `parse_s2s_reference()` read anything starting with a digit as a timestamp. BEFORE, AFTER, AROUND and BETWEEN with `msgid=<such an id>` were answered from a nonsense time. 80859cb removed the T/M markers on the premise that msgids never start with a digit.

Changes:

- **The requester sends a msgid reference as `msgid=<id>`.** Responders have read that marker since 400a39f, so older ones accept it too. Timestamps stay bare.
- **The responder reads a bare reference as a timestamp only when it has a timestamp's shape** (unix `sec[.ms]` or ISO 8601). A bare msgid from an older requester is then read correctly as well. Only a msgid of fourteen digits would still be misread, and none can exist before 2083: a msgid carries its mint time, which is all digits only from then on.
- **An empty `msgid=` is refused before any query goes out.**
- **The three functions move to `chathistory_ref.c`** (`chathistory_valid_timestamp`, `chathistory_ref_to_s2s`, `chathistory_parse_s2s_ref`) so a CMocka suite can link them alone. `chathistory_ref_cmocka` covers both sides and the round trip. Five of its ten cases fail when the two old function bodies are restored.

Testing: build and all CMocka suites pass.

**Added since opening:** the responder refuses an empty `msgid=` or `timestamp=` too, so an empty reference is never run as a query. No requester is known to send one. `chathistory_ref_cmocka` checks this.

**Changed after review:** a reference the responder cannot parse (an empty marker among them) is answered `E <reqid> 0 U`, not a bare `E <reqid> 0`. Nothing was looked up, so the requester's page is marked partial instead of complete.

**Mixed builds** (run): a requester with this PR and an older responder, and an older requester with a responder with this PR, both give correct pages. Only an older requester with an older responder stays wrong, until the responder is upgraded.

**Changed after the second review:** BETWEEN's second reference is held to the same rule. One that is missing or does not parse answers `E <reqid> 0 U`, as it did before this PR, not a bare `E <reqid> 0`.

**With #242:** the two conflict textually in `ms_chathistory()`: #242 adds a check that calls the parser this PR renames to `chathistory_parse_s2s_ref()`. The second to land rebases.
