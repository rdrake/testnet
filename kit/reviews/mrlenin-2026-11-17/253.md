Reviewed at 40b50f73. Built with no warnings, all 96 CMocka suites pass, and CAP LS and the subcommands were run on a scratch server, tip against this head, also under ASan (no report). The restore batch was not exercised at runtime: in that setup neither the tip nor this head replayed a held session's channels on revive, so everything below about the batch type was established by reading both sides, this server and Seance.

1. Deployed Seance stops recognising a held session's restore. The batch type changes from `draft/persistence` to `evilnet.github.io/persistence` for every connection, with no transition (`PERSISTENCE_RESTORE_BATCH`, `include/bouncer_session.h:32`, opened in `bounce_send_channel_state()`, `ircd/bouncer_session.c:18456`). Seance's develop branch registers its batch handler for `draft/persistence` only (`client/js/irc/handlers/index.ts`) and its restoration check compares against that name (`client/js/irc/persistence.ts`). So its restoration handler does not run, autojoin is not held for it, and the restored JOINs read as live activity ("held sessions would stop restoring quietly", as evilnet/seance#327 puts it). Likewise `attach-cursor` leaves the `draft/persistence` value (`ircd/ircd.c:1350`), and Seance reads it from there only, so it stops sending `PERSISTENCE ATTACH default <msgid>` and catches up by itself (a degradation, not a failure). The subcommands get a transition (`PERSISTENCE_DRAFT_EXTRAS`); the batch type and the value need one too, or a stated ordering with Seance (see below).
2. The extras now fail for a client with neither capability, although they worked before. At the tip `PERSISTENCE LIST` and `PERSISTENCE PROFILE LIST` were answered for a client that negotiated nothing; here it gets `FAIL PERSISTENCE INVALID_PARAMETERS LIST :Unknown PERSISTENCE subcommand`, also with `PERSISTENCE_DRAFT_EXTRAS` on (`persistence_extras_allowed()`, `ircd/m_persistence.c:1008-1016`, gate at :1050). Run. A script, or an oper typing `/quote PERSISTENCE LIST`, loses it, and the description does not say so.
3. A testnet test breaks that the description does not name: both cases of `tests/src/ircv3/persistence-batch.test.ts` expect `BATCH +<ref> draft/persistence`, besides the `draft/bouncer` case in `bouncer.test.ts` you mention. The other suites use the extras with `draft/persistence`, which keeps working while the flag is on.

**Description:**
- "Seance already requests both capabilities, reads `attach-cursor` from either one's value, and accepts either batch type": true only of evilnet/seance#327, an unmerged draft. Seance develop requests `draft/persistence` only, reads `attach-cursor` from its value only, and accepts only the `draft/persistence` batch.
- "STATUS, GET and SET ... already follow the spec": SET still sends a `PERSISTENCE SET ON|OFF|DEFAULT` line before the STATUS (`send_persistence_reply()`, :166, called at :313, :333, :346); the spec answers SET with STATUS only. Drop the line, or list it as a deviation.
- The comment at :1044-1049 says a FAIL for an unknown subcommand is what "the spec's own server would answer"; the spec says implementations "SHOULD ignore unrecognized subcommands".
- The account metadata keys (`draft/persistence/hold`, `.../auto-replay`, `.../profile/*`) keep their names. That is defensible, since renaming them is a disk and S2S migration, but say so.

**Mixed builds:** nothing changes on the S2S wire or on disk. On rollback, a config that sets `CAP_evilnet_persistence` or `PERSISTENCE_DRAFT_EXTRAS` gets a harmless "Unknown feature" CONFIG error.

Not decided on our side yet:
- Whether the extras (ATTACH, DETACH, LIST, PROFILE, REPLAY) stay subcommands of `PERSISTENCE` under the vendor capability, as here, or move to a vendor command of their own.
- Whether cap-less use of the extras ends with this change, or only when `PERSISTENCE_DRAFT_EXTRAS` goes FALSE.
- The transition for the restore batch type: send the vendor type only to a connection that negotiated `evilnet.github.io/persistence` and the old type otherwise while the flag is on; or have evilnet/seance#327 merged and deployed first, with that ordering stated here.
- The capability's name form: `evilnet.github.io/persistence` (a DNS name before the slash, like the existing `evilnet.github.io/...` batch and tag names), or the `evilnet/<name>` form that `evilnet/channel-relocate` uses.
