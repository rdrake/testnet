1. **One client can take 48 of the 64 federation slots, and then its own and every other user's no-`in=` searches are answered from this store only, with no error.** Run: a client in 8 channels whose rows only the peer holds sent seven `SEARCH` lines in one write. Searches 1-6 each federated 8 parts (48 `CH Q S` lines) and returned 8 of 8 rows; search 7 returned an empty batch (0 of 8) and no `FAIL`. With the one-search-in-flight rule (removed in 9a965499) the second search was the one answered locally. With the default fake lag a client still gets about five `SEARCH` lines through in one burst: 40 parts, that is 40 full 50,000-row walks queued on every storage peer by one client. #296 moves those walks off the main loop but does not bound how many one client queues. Fix: count the client's in-flight `complete_search_agg_part` requests in the slot loop (`ircd/m_chathistory.c:9963`, check at :9978) and cap them at `SEARCH_FED_PARTS_MAX`; answer a search that cannot get its parts with `FAIL SEARCH TEMPORARILY_UNAVAILABLE` (or a `NOTE`) instead of a silent local-only batch.

2. **801ac5c5 (presence filter on the responders' rows): works, and needs a test.** Run on two linked servers with `CHATHISTORY_STRICT_PRESENCE` on: both forms now return only rows inside the requester's presence, for a requester with and without an account and for a bouncer device; with the feature off, and for plain federation, results are identical to before. By reading: the filter runs before the merge and the limit cut on every path the responders' rows take (`complete_search_fed`, each `complete_search_agg_part`, the timeout path), and a requester that has gone gets nothing. Asks: a two-server test (a row stored only on the peer before the requester joins and one after; each form returns only the second; both with the feature off); and one sentence in the description that a page can come back short, since a responder cuts to `limit` before this server filters and SEARCH has no partial marker. Over-fetching to avoid that would be more machinery than the case needs.

3. Optional, plausible, by reading: `search_fed_line_fits()` probes with request id `fed_reqid_counter + 1` (`ircd/m_chathistory.c:8164`), but the parts take `+1, +2, ...` (:8208). When the counter gains a digit inside one search (…9 to …10), a line that passed the probe by one byte fails `start_fed_search()`'s re-check (:8204) and that channel is answered locally, silently. Fix: probe with the width of `fed_reqid_counter + SEARCH_FED_PARTS_MAX`, or skip the re-check for a pre-checked query.
