# #276 chathistory: a renamed channel's history follows it to the new name

Head when copied: 2ad4eca5

## MrLenin, 2026-11-18T19:08:05Z

Reviewed at 2ad4eca5. Built with `--enable-debug` (no warnings), the CMocka suites pass (97 programs, the new ones included), and rename cases were run on one server and on two linked fork servers (re-created names in both directions, a `#a→#b→#c→#a` cycle, a rename onto a dead name, a store down during the rename: all as described); not run: ASan, SEARCH across a rename, clock skew, a split.

Where this stands on our side: RENAME is low priority for now, though it needs sorting out eventually. The bigger concern with RENAME is desyncs and corrupted state between servers, more than what happens to history.

1. **Each server takes the rename's time from its own clock, so servers disagree on the boundary.** Plausible, traced, not run. `history_rename_until()` (`ircd/history.c:4442-4451`) sets `until_ms` from `history_recv_now_ms()`, and `presence_on_channel_rename()` moves intervals at `presence_now_time()` (`ircd/chathistory_presence.c:1623`), while rows carry the sender's HLC stamp. With strict presence, a row stored under the new name by a server whose clock lags falls before the members' new-name interval and is hidden from members who were there all along. For a relocation, tombstone rows from a lagging server can fall inside one store's `#new` segment and outside another's. Fix: take the time from the RN line (`history_event_time_ms(cptr)` when it carries one; mint and relay one otherwise) and pass it to both functions.

2. **After a rename that only one side of a split executed, a lost burst deletes rows another live channel still owns.** Plausible, traced, not run. `history_purge_incarnation()` now also purges the earlier names (`ircd/history.c:3166-3168`). If the renamed channel loses a burst on that side, the other side's burst brings `#old` back with the same incarnation, but this store has just deleted `#old`'s rows up to `until_ms`. Same for a relocation whose tombstone is still live. The tip prunes only the losing name. Fix: drop that loop (keep `hren_forget()`), or skip a segment whose name a live channel of the same incarnation holds.

3. **The description is out of date after 3ac1fc93** (by reading): "When the store fails" describes the removed distrust mark and retried delete; "An account's two records change in one write" describes the removed one-batch move; `chathistory_presence_store_cmocka` no longer exists; `history_read_cmocka` has 16 cases, not 15.

4. **Channels never renamed pay for it** (by reading). The trim's renamed-parent callback (`ircd/history_trim.c:1766`) runs for every evicted REDACT row whose original is already gone, the normal case, with no short cut: a `db_get` plus a msgid-index seek each. Every TARGETS listing does one renames `db_get` per channel (`ircd/history.c:3476`; the one-entry cache thrashes), and each trim pass scans the whole renames column family. Fix: skip the callback when the channel has no record, and cache "no record" per name.

5. Records this build cannot decode, including the version-1 records earlier pushes wrote, are never deleted: `hren_sweep()` skips them (`ircd/history_rename.c:700-703`). Delete older versions there. By reading.

6. A REDACT row removed through `delete_index_only()` leaves its `'L'` entry behind for good: the returns at `ircd/history_trim.c:1944` and `:1948` come before the `'O'` value is read. By reading.

Where this can run: RENAME is refused while a stock server is linked (`rename_legacy_blocker()`, `ircd/m_rename.c:4134-4141`), so on a network that still links stock servers none of this is reached.

With #241: if this goes in after #241, `history_lookup_live_message()` applies `row_incarnation_ok()` against the live channel to whatever `history_lookup_message()` returns, now including rows under an earlier name. It must judge such a row by that rename segment's incarnation, or skip the test as your walks do (`ircd/history.c:2500-2503`). The two merge cleanly, so nothing flags it (by reading).

The presence part (`presence_on_channel_rename()`, about 60 lines) is needed whichever way history goes and can be split into its own PR. Simpler alternatives for history exist (clear the old name's rows at RENAME, about 30 lines; or leave them as today), and what users see is the same under both.
