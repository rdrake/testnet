Live delivery was correct on every path run, only status holders receiving each line, one msgid throughout: fork to fork; a stock (master) server between two servers with this PR; this PR against a fork server on the current tip, both directions; a rollback of the store; `NOTICE @#chan` now honouring `+N` and `+c`; multiline to a status target refused (`401`) on both.

Not decided on our side yet: should status messages be stored in history at all? Q1-Q17 do not cover it.
- (a) Not stored, as the tip does on purpose: keep the wire change and the NOTICE checks; the history half goes (row types, mask plumbing, `CH W` letters, the `CH Q X` change; roughly 450 lines).
- (b) Stored, readable by whoever holds the status when they ask, as this PR does: a member opped later reads the whole ops backlog from while they were a plain member (run, also under strict presence), and a deopped op loses access.
- (c) Stored, readable only by members who held the status when it was sent: needs status in presence tracking, not written.

If storage stays:

1. A REDACT of a stored status message goes to the whole channel and is replayed to everyone. Run: an op's `REDACT #sm <msgid of a PRIVMSG @#sm> :reason` reached every non-op and the voiced member, went over the link as `RD`, and CHATHISTORY replayed the REDACT row to a non-op, who learns that an ops-only message existed, its msgid, time, redacter and reason. On the tip the same REDACT fails with `UNKNOWN_MSGID`. The description calls this a known limit, but it is new exposure. `redact_authorize()` (`ircd/redact_index.c:235`) and `hm_redactable()` (`ircd/chathistory_merge.c:594`) accept status types via `history_type_base()`. Fix: return `REDACT_AUTH_NOT_MESSAGE` for `history_type_is_statusmsg(in->msg_type)` (about 2 lines) and answer a status row with `Message not found`, as for an unknown msgid, in `m_redact()` (`ircd/m_redact.c:298`) and `complete_redact_fed()` (`ircd/m_chathistory.c:7099`).

2. The local REDACT lookup tells a non-holder whether a status msgid exists. Run: a non-op's REDACT of an ops-only msgid gets `REDACT_FORBIDDEN … not authorized`; a made-up one gets `UNKNOWN_MSGID … Message not found`. `history_lookup_message()` at `ircd/m_redact.c:253` ignores the requester's mask, so the description's "cannot be confirmed to a reader without the status" holds only for `CH Q X`. Fixed by 1; otherwise treat a row whose type `requester_type_mask()` does not name as `rc = 1` there.

3. Status rows do not update the TARGETS timestamp (`ircd/history.c:1724`, on purpose), so a client that decides its catch-up from TARGETS can skip a channel whose only new lines are status messages. By reading. At least document it.

4. No unit test pins the read filter deciding who sees status rows: `statusmsg_type_bits()` (`ircd/m_chathistory.c:721`), `requester_type_mask()` with a target (`:754`), a 0 or absent `CH Q` mask meaning "no status types".

Rollback: a tip binary on this PR's store hides the status rows from every reader (run).

Mixed builds: stock servers, and services behind them, get exactly today's wall line. During an upgrade window nothing is lost or misdelivered; NOTICE shows an `@ ` lead on older servers and none on servers with this PR.

With #252: this PR makes it `requester_type_mask(sptr, target)`, adds the status types held in that channel, and never returns 0. #252's `search_fed_line_fits()` prints the mask into a probe `CH Q S` line to check the 510-byte limit; the second to go in must pass there the channel `start_fed_search()` sends, per channel. The mask can now reach `7ffff`, 4 bytes longer, so a probe with another mask could pass a line that is then cut. The arity change forces a compile error, but a fixed target would compile.
