# #283 cap: NAK a CAP REQ for a capability that is not offered

Head when copied: 850a18b0

## MrLenin, 2026-11-18T19:11:14Z

Reviewed at 850a18b0. Built with `--enable-debug`, the whole CMocka suite passes (98 suites), and the cases below were run on a scratch server at this head and at the tip 426b2808, with a fake services server linking and splitting. Not run: irctest, ASan, a multi-server topology.

Not decided on our side yet: should a `CAP REQ` naming a capability that is not offered at that moment be NAKed whole
- (A) for everything, as this PR does, including capabilities that are only away for the moment (`sasl` while services are away or not yet linked, `draft/authtoken` with no service);
- (B) only for what is off for good (feature off, hidden, prohibited), still ACKing the ones only away for the moment;
- (C) not at all: keep today's ACK and take only the CAP NEW and feature-notifier fixes.

For a client that requests a fixed list without reading CAP LS: under (A) it runs with no capabilities at all while any one of its list is away. Run: boot before services link, `CAP REQ :server-time message-tags sasl`; the tip ACKs all three, this PR NAKs all three, and `CAP LIST` is empty after 001. Under (B) it keeps its other capabilities through a services split; its AUTHENTICATE fails as today. Under (C) nothing changes.

Whatever is chosen:

1. **`cap-notify` must always be ACKed to a CAP 302 client.** Run: with `CAP_cap_notify` off, `CAP LS 302` then `CAP REQ :server-time cap-notify` is NAKed whole, though the spec says servers "MUST accept and `CAP ACK` the request" and this server still sends NEW/DEL to 302 clients (`cap_notify_wanted()`). Fix in `cap_offered_at()` (`ircd/m_cap.c:664`), before the feature test:
   ```c
   if (cap->cap == CAP_CAPNOTIFY && version >= CAP_VERSION_302)
     return 1;
   ```
2. **The irctest controller change your description says is needed is not in the PR.** By reading: `tools/irctest/nefarious.py` sets neither `CAP_draft_event_playback` nor `CAP_draft_account_registration`, and irctest's chathistory tests request `draft/event-playback`, so those cases now NAK. Add `"CAP_draft_event_playback" = "TRUE";` there (and the account-registration one, if those tests should run).
3. **No client can get `evilnet/channel-relocate` unless the default or the comment changes.** `CAP_evilnet_channel_relocate` defaults to FALSE (`ircd/ircd_features.c:1395`), while its comment says it is "Advertised whenever the build supports it". The tip ACKed a REQ for it anyway; this PR NAKs it (run). Flip the default to 1, or keep 0, fix the comment and tell operators.
4. **A DELed capability stays in the client's set.** Run; older than this PR, but your "already held" rule leans on it: after `CAP DEL :sasl`, `CAP LIST` still shows `sasl` and a re-REQ is ACKed (`cap_req()`, `ircd/m_cap.c:875`) while it is not offered. Same after a REHASH DEL. The spec says servers "MUST cancel any capability-specific behavior" after sending `CAP DEL`. Fix: where DEL is sent, clear the capability from each recipient's set, with `cap_dependents_drop()` and the bouncer recompute.

Could be simpler: `cap_announced` (about 25 lines in `send_cap_notify()`, `cap_notify_flush()` and `send_caplist()`) only avoids a DEL that clients ignore ("stop over-engineering where it isn't necessary"), and collides with #249's `cap_announced`, which means something else.

Description:
- The quoted MUST ("is not supported or cannot be enabled") is not in the current `capability-negotiation.md`, which says only that the set "must be accepted as a whole, or rejected entirely".
- The `con_capab_told` paragraph and "`client.h` gains a field" are stale since 044b84b2.
- "Before, switching `CAP_sasl` or `CAP_draft_webpush` off sent DEL to every cap-notify client": at the tip neither feature had a notifier, so switching them sent nothing.
- The `account_registration` tests skip only because the controller never turns `CAP_draft_account_registration` on; they still exercise nothing.

Landing order, as a technical dependency: #289, #288, #249, #253, then this one, rebased onto #249's `cap_announced`.
- With #288: one conflicting hunk in `send_caplist()`; resolve as your `cap_offered_to()` plus #288's `cap_ls_left_out()` filter.
- With #249: seven hunks (both `cap_announced`s, `cap_notify_flush()`, the REQ refusal); a hand merge to one set with one meaning.

## MrLenin, 2026-11-18T19:13:54Z

Correction to the question at the top of my review: it is not open. NAKing the whole request is the spec's rule ("The capability identifier set must be accepted as a whole, or rejected entirely"), so what this PR does, option (A), is right, including for a capability that is away at that moment and so is not in `CAP LS`. A client that requests a fixed list without reading `CAP LS` is the one out of step with the spec.

Items 1-4, the description points and the landing order are unaffected.
