1. **Regression against the tip: a tagged CLEARMODE makes receivers send several MODE lines under one msgid, and their history loses rows.** 129e0598 has the origin take `generate_msgid_ahead()` (`ircd/m_clearmode.c:183-184`) and relay the CLEARMODE tagged with it (:324-327). A receiver's modebuf has the link as `mb_connect` (:173), and `modebuf_flush_int()` reuses the link's msgid for every flush (`ircd/channel.c:3060-3064`, existing code). Run: `CLEARMODE #c ob` by an oper on A, 8 ops and 10 bans, both on this head:
   ```
   A: ABAAAaHv8oy2h6 MODE #c -bbbbbb ...   B: ABAAAaHv8oy2h6
   A: ABAABaHv8oy2h7 MODE #c -bbbboo ...   B: ABAAAaHv8oy2h6
   A: ABAAAaHv8oy3h8 MODE #c -oooooo ...   B: ABAAAaHv8oy2h6
   A: ABAABaHv8oy3h9 MODE #c -o cA         B: ABAAAaHv8oy2h6
   ```
   B's `CHATHISTORY LATEST #c` then has `h6` as `-o cA` (overwritten by the last flush); the `-bbbbbb` row is gone. A client that deduplicates by msgid drops three of B's four lines and keeps stale op and ban state. On the tip, B mints one id per line. A receiver on the current tip behind an origin on this head duplicates the same way (run), since the reuse is tip code: both ends matter. Fix, one of:
   - drop 129e0598: a `CLEARMODE ... D` reveal stays per-server, as on the tip (`JOIN_ON_REMOVEDELAY` is off by default);
   - or reuse the link's msgid for a modebuf's first flush only (a flag in `struct ModeBuf`), mint for later ones, and have that on every fork server before any server sends a tagged CLEARMODE.
2. **Please move the build-system commits (8823b235, a4884cdc) to their own PR.** They are another subject, and the reason for them here (the earlier `struct Connection` change) is gone. They work as tested: in-tree and out-of-tree with gcc, `.d` files only in the build directory, a touched `include/crdt_hlc.h` rebuilds 11 objects. BSD make was not tried (INSTALL requires GNU make).
3. Low, plausible by reading: the origin's JOIN derives from the next mint, not this event's. `generate_msgid()` (`ircd/send.c:776`) hands the ahead id to whichever caller mints first. Every caller traced mints the event next; nothing enforces it: a mint in between (`sendcmdto_one_tags()`, :1956, or an `hlc_global_event()` user such as metadata or forwarded labels) would give the origin a JOIN msgid no other server has. Suggested: log or assert when another command takes the ahead id, or pass the event's id explicitly, as `m_batch.c` does.

The origin reveals the device (`relay_channel_message()`, `ircd/ircd_relay.c:1021`) and derives from the alias's numeric; receivers rewrite to the primary (`server_relay_channel_message()`, :1317-1318) and derive from its numeric. Derive from the same numeric everywhere, or add it to Limits.
